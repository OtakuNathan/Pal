Engineering Review of the Pal and pal-shell-native Tool Contract

Executive Summary

1. The highest priority is unifying our own public aliases into "verb + accurate object". This review exhaustively lists 223 distinct fixed candidate names and gives a rename or keep recommendation for each; this includes Bunshin role-scoped tools and does not mean 223 tools are exposed simultaneously in the same session. Names must express the real action; mixed read/write entry points must not all be renamed to get.
2. Search benefit must distinguish "word-order match" from "keyword coverage". The current alias word matching ignores order, so pure reordering does not improve that tier; only adding action words and object words can change coverage. Exact matching, prefix matching, and equal-score ordering are also affected by renames. No search or model-behavior benchmark has been executed, so no hit-rate improvement can be promised.
3. The second priority is making diagnostic facts actually reach the model body. This review confirms 10 concrete categories of loss, plus 1 conditional recovery-prompt gap. First fix native blocked sessions and normalization coverage, write_file/delete_path reason loss, and similar paths; keep bounded diagnostics and safe recovery pointers, and do not unconditionally feed back all internal structured data into context.
4. Parameter relationships must be documented according to the actual implementation, distinguishing hard rejections, silent precedence/ignoring, and run-state preconditions. The shell_session action whitelist and identifier mutual exclusion especially need a complete description; several Bunshin task fields' existing descriptions are inconsistent with the actual actor-unique active Task selection. The appendix lists 43 check items, including correctly documented rules and normal combinations, which does not equal 43 defects; each item gives the current state, recommended description, and rationale.
5. Explanations of success paths should live in stable descriptions or success results. remote_start's action completion does not prove the target is ready; remote_power's accepted/unknown does not prove shutdown completed. Empty-result explanations, valid-target boundaries, usage unknown, and similar items should not rely solely on failure guidance to trigger. Semantics already visible in schema, skill, context_messages, or success payloads are flagged separately to avoid false positives.

Reading Order

- Appendix A: naming and search mechanisms, the complete current alias → recommended name list, shell_session split options, and dynamic name boundaries
- Appendix B: at which layer diagnostic information is lost, what the model actually sees, minimal fixes; confirmations and counterexamples for success semantics
- Appendix C: the complete list of parameter combinations and state constraints, directly usable description suggestions, and combinations that should remain free

Review Nature

This is a read-only static review of a fixed source version. Project source was not modified, the project was not installed or run, no tests were run, and actual model behavior was not measured. All renames, splits, descriptions, and rendering changes are recommendations pending implementation. Acceptance at rollout should target the final model body and the actually exported directory.

Appendix A: Complete Naming and Search Inventory

Search Scoring: What Renaming Can and Cannot Do

Based on runtime.py (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/runtime.py#L1003-L1096) and discovery_terms.py (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/discovery_terms.py#L10-L29):

1. query/alias are lowercased; tokenized and split by underscore, dot, and hyphen; lightweight singular/plural normalization; sets are used, word order is not considered. No general semantic vector retrieval or word-sense understanding
2. tier 5: the query exactly equals the full alias
3. tier 4: the query word set equals the alias word set
4. tier 3: all query words are in the alias, or a space-free query is a prefix of the alias
5. tier 2: the alias and purpose combined cover all query words
6. tier 1: at least one word is covered by the alias or purpose; items with no coverage are not returned
7. score = tier × 10000 + total covered words × 100 + alias-covered words × 10 + purpose-covered words; actual ordering is descending by these components, then by alias lexicographic order
8. namespace/family/module/tags are filter conditions, not positive task-matching words. Although the compiled search_document contains more fields, the current scoring code uses only alias and purpose; use_when, failure_next_steps, schema, and so on also do not participate in positive scoring
9. Default return limit is 3; when no limit is explicitly passed and the highest tier ≥ 2, only the highest tier is kept. Renaming may change which results are returned and may change the lexicographic tie-break, but is not unconditionally better

For example, browser_read → read_browser_page adds page, directly covering "read browser page"; browser_read → read_browser only reorders and yields no tier benefit for "browser read". browser_history → navigate_browser_history and splitting shell_session into action aliases put real actions into the alias, whereas uniformly naming mixed read/write tools get_* would mislead call decisions.

Migration notes: the current capability enforces "exactly one public alias", so old and new names cannot simply be added together in aliases. Backward compatibility with old names requires a separately designed resolution/migration mechanism; this review does not recommend changing internal addressing. Guidance, next-tool hints, returned affordances, examples, the parts of role allowlists that actually use aliases, and tests/docs must also be updated in sync to prevent recovery paths that still prompt the old name.

Splitting shell_session: design options, not yet implemented

The suggested split of "action + shell_session" can map completely to the existing eight actions. The following are design options, not yet implemented:
- read → read_shell_session: may carry wait_ms; failed output can be re-exported for retry, but the command will not be re-run
- write → write_shell_session: must carry text; PTY input has a 64KiB limit
- resize → resize_shell_session: must carry rows and columns
- terminate → terminate_shell_session: requests termination; not equivalent to having already terminated
- release → release_shell_session: discards retained output of a completed session; releasing a running session is not allowed, and this is not equivalent to terminate
- watch → watch_shell_session: must have a positive wait_ms, may carry extend_by_ms
- extend → extend_shell_session: must have a positive extend_by_ms; only extends an existing finite deadline, and no extension is needed when there is no deadline; this is not a plain wait
- unwatch → unwatch_shell_session: disables subsequent proactive notifications; not equivalent to stopping the process

NativeSessionInput requires exactly one of session_id or output_ref. output_ref is only supported by read/release, and wait_ms is not allowed. Therefore, the split must preserve this mutual-exclusion constraint and the output recovery entry point; read/release may keep output_ref or introduce a dedicated output alias. The existing unified entry is INDIRECT_CONTROL; splitting requires independent schema/execution semantics/affordance design — correct read-only or retry properties cannot be obtained automatically by renaming.

Appendix B: Model-Visible Diagnostics and Success Semantics

Scope and Basis of Conclusions

The scope is Pal's built-in tools, in-repo declarations, and native's Python host/remote bridge plus related C++ rejection production points. It does not cover user-deployed custom plugins, standalone eye implementations, or other third-party tools for which no source code was obtained.

Conclusions come from static source-code paths. "Possible misjudgment / one extra call" was not written up as measured model behavior; not every field present in structured but absent from the body was uniformly treated as a defect. Execution status, failure body, recovery hints, input contracts, independent context_messages, and on-demand readable detail/skill were all included in the judgment.

Summary: List One enumerates 10 categories of concrete diagnostic information loss, plus 1 conditional recovery-hint gap. List Two distinguishes confirmed default-success-path semantic gaps, semantics declared in a poor location but present elsewhere, and low-priority empty-result explanations/next-step suggestions. Items are grouped by cause; the category counts must not be treated as counts of defective call sites.

Common Rendering Chain: Why structured Does Not Equal What the Model Sees

- The default description compiles only purpose/use_when/do_not_use_when, execution semantics, example, and next-tool hints; it does not compile failure_next_steps: src/pal/execution/tool_facade.py:264-291 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/tool_facade.py#L264-L291)
- An ordinary CapabilityResult failure puts raw.text into error, raw.llm_text into llm_text, and raw.structured into details: src/pal/execution/runtime.py:1409-1454 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/runtime.py#L1409-L1454)
- The final model body is llm_text + a metadata tail; the tail lists only kind/effect/error_code/retry/recovery/affordances, not error or details: src/pal/execution/runtime.py:1585-1660 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/runtime.py#L1585-L1660)
- The turn executor directly adopts llm_text with priority: src/pal/core/turn_executor.py:1704-1709 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/core/turn_executor.py#L1704-L1709)
- failure_next_steps only serves as a fallback for ordinary failures when the handler has no recovery_hint/affordances; it is not triggered on success; ToolRejectedError also does not automatically add the descriptor fallback: src/pal/execution/result_guidance.py:112-130 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/result_guidance.py#L112-L130), src/pal/execution/runtime.py:789-792 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/runtime.py#L789-L792), src/pal/execution/runtime.py:1532-1541 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/runtime.py#L1532-L1541)

This is a reasonable single-body design. The fix should be in the producer's factual projection or a bounded diagnostics interface; one should not simply stuff the entire structured/details back into the prompt unconditionally.

List One: Real Diagnostic Losses

A1 · native hides non-empty blocking_sessions and thereby removes the recovery entry point · P1

Production info: The write_busy/result_capacity branches of ShellRejected collect the locally tracked session_id, latest_status, and watching into details.blocking_sessions. The shell_status affordance is only added when the list is empty: pal_plugin/pal_shell_native/runtime.py:456-479 (https://github.com/OtakuNathan/pal-shell-native/blob/f307c9614634dd62a97bd1429d967a1c55489896/pal_plugin/pal_shell_native/runtime.py#L456-L479)

What the model actually sees: The raw exception string + rejected/error_code/retry metadata. The IDs/status/watching of a non-empty list do not appear in the body, and there is no shell_status affordance; this rejection branch does not add the run_shell/session failure fallback.

Specific cases that cannot be generalized:
- The write_busy original text in host runtime.py:423 is only "shell results are not ready yet", with no IDs; here the IDs and status are indeed entirely lost: pal_plugin/pal_shell_native/runtime.py:422-423 (https://github.com/OtakuNathan/pal-shell-native/blob/f307c9614634dd62a97bd1429d967a1c55489896/pal_plugin/pal_shell_native/runtime.py#L422-L423)
- The C++ begin/acquire_write write_busy text already contains the writer id, so it cannot be said that blocking IDs are entirely lost on those paths; however, the status/watching and other session information in the structured list are still not projected: runtime.cpp:476-483 (https://github.com/OtakuNathan/pal-shell-native/blob/f307c9614634dd62a97bd1429d967a1c55489896/runtime.cpp#L476-L483), runtime.cpp:673-677 (https://github.com/OtakuNathan/pal-shell-native/blob/f307c9614634dd62a97bd1429d967a1c55489896/runtime.cpp#L673-L677)
- The C++ text for result_capacity only says acknowledge/release completed results, without specific sessions: runtime.cpp:480-483 (https://github.com/OtakuNathan/pal-shell-native/blob/f307c9614634dd62a97bd1429d967a1c55489896/runtime.cpp#L480-L483)
- blocking_sessions is the set of locally tracked sessions; it does not prove that every entry is a currently real blocker, and the fix should not label all of them "confirmed blockers".

Minimal fix: Display a bounded tracked_sessions list in the body along with its observation time/non-causal note, or keep the shell_status read entry regardless of whether the list is empty. Do not automatically terminate/release based on the list, and do not unconditionally treat the writer lease ID as a session ID.

A2 · native exhaustion: after normalization recovery, generalized text overwrites the original detailed failure · P1

Production info: Pal's ordinary output_validation_failed body contains Validation error, the unverified output, and the original llm_text; after native receives a non-CompleteResult, it retries normalization only twice; if it still fails, it replaces llm_text with "The command result could not be delivered. Do not rerun the command to retrieve output.": src/pal/execution/runtime.py:1493-1510 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/runtime.py#L1493-L1510), pal_plugin/pal_shell_native/runtime.py:530-555 (https://github.com/OtakuNathan/pal-shell-native/blob/f307c9614634dd62a97bd1429d967a1c55489896/pal_plugin/pal_shell_native/runtime.py#L530-L555)

What the model actually sees: the generalized delivery failure + the original error_code/retry/effect metadata. The original error/details is not re-displayed by the public renderer; being retained internally is not the same as being visible. Even if a snapshot was previously generated, it is not guaranteed that the replaced body still provides a usable read pointer.

Lost: which specific field/type failed validation, the original command result body, and output evidence needed to fix the contract. The protection against rerunning the command is still visible, so it cannot be claimed that this protection was also lost.

Minimal fix: Keep the original detailed failure body and append a delivery-failure warning; ensure that the retained output's session_id or output_ref and the safe re-export entry remain visible. Do not run the handler again.

A3 · write_file shrinks specific filesystem errors into "Failed to write file." · P1

Production info: resolve, mkdir, and atomic create/overwrite catch OSError/ValueError with the original exception stored in structured.details; _err always uses _ERROR_LLMS: src/pal/execution/file_write.py:75-79 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/file_write.py#L75-L79), src/pal/execution/file_write.py:91-111 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/file_write.py#L91-L111), src/pal/execution/file_write.py:126-137 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/file_write.py#L126-L137), src/pal/execution/file_write.py:179-183 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/file_write.py#L179-L183)

What the model actually sees: "Failed to write file.", WRITE_FAILED, and effect/retry, plus the general fallback for file tools; it cannot see exception text such as errno or permission/read-only/disk-full/specific failure location.

Minimal fix: Add a bounded, appropriately sanitized operation phase + exception type/errno/message to the body, and for persistent errors where the replace may already have completed, explicitly state "commit result is uncertain; read the current file first". Do not assert that nothing was written based on a generic error.

A4 · delete_path hides the root cause of failure; the directory SHA check also displays the wrong corrective direction · P1/P2

Production info: resolve/read/unlink/rmtree failures put str(exc) into structured.details; SHA mismatch stores both the current and expected digests; when expected_sha256 is passed for a directory, details explicitly states "sha256 is only supported for files": src/pal/execution/path_delete.py:55-104 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/path_delete.py#L55-L104)

What the model actually sees: "Failed to delete path." or "Failed to read file before deleting."; yet the directory SHA branch displays "expected_sha256 must be a 64-character hexadecimal SHA-256 digest.", even when the supplied digest is itself valid. The specific filesystem exception, the fact that directories do not support that parameter, and the current digest are all not rendered: src/pal/execution/path_delete.py:28-38 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/path_delete.py#L28-L38), src/pal/execution/path_delete.py:125-128 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/path_delete.py#L125-L128)

Minimal fix: Distinguish invalid_digest_format from digest_not_supported_for_directory; display a bounded reason in the error body. The current digest may be presented as diagnostics, but do not imply blindly replacing the digest and deleting; file identity/content still needs to be verified. The omission of the digest itself has lower priority than the misreporting of the error cause.

A5 · channel_enable/channel_disable persistence failure swallows the specific exception · P2

Production info: after rolling back the runtime enabled state, text contains "channel endpoint state update failed: {exc}", and structured has endpoint_id/previous_enabled; llm_text only says the durable state could not be committed: src/pal/channel/capabilities.py:730-745 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/channel/capabilities.py#L730-L745)

Lost: the specific repository/I/O failure reason, details such as the endpoint having disappeared, and the rolled-back enabled value. The endpoint name is already present in the request, so its non-repetition is not counted as a major loss.

Minimal fix: Add the bounded exception reason and the final enabled state to llm_text; keep the current "not committed, rolled back" semantics.

A6 · built-in tool output validation failure leaves only a single-line heading · P2

Production info: _complete_builtin catches ValidationError/TypeError and saves error=str(exc) and details.output_schema, but llm_text contains only "Built-in output failed validation for {alias}.": src/pal/execution/runtime.py:1114-1135 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/runtime.py#L1114-L1135)

What the model actually sees: the heading plus output_validation_failed/effect/retry, with no knowledge of the failed field, type, or requirement. This differs from the ordinary handler branch, which already explicitly writes the validation exception and the original result into the body.

Minimal fix: Reuse the ordinary output-validation renderer, at minimum projecting the field path, expected/actual types, and a bounded reason, and preserve a safe way to read the original output. This item is a static proof about the conditional branch and does not mean that normal builtins currently trigger this error in production.

Minimal fix: Display a bounded list of valid values/the target argument name in the body; if the list is too long, provide an explicit pagination/listing entry. With discovery already available it is an extra round trip, not an absolute inability to recover.

A8 · output_schema being trimmed normally is reasonable, but on contract errors there is no model-usable full repair view · P2

Production info: read_tool's internal payload does contain output_schema; render_tool_definition explicitly removes output_schema/example: src/pal/execution/runtime.py:1098-1111 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/runtime.py#L1098-L1111), src/pal/execution/tool_presentation.py:42-46 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/tool_presentation.py#L42-L46)

Specific gap: the repair suggestion for output_validation_failed requires fixing the provider/output contract, yet neither its details.output_schema nor the subsequent read_tool's output_schema is displayed. Minimal fix: Add an output/detail view to read_tool, or on validation errors output the relevant schema subtree plus an entry to read the full contract; do not restore every ordinary tool discovery into the full output schema.

A10 · The remote SSH/start subprocess stderr is sent to DEVNULL, leaving no evidence available for later presentation · P2

Production information: The SSH tunnel uses stderr=DEVNULL and after exit only throws a generalized authentication/forwarding failed; the explicit start action's stdout/stderr are also DEVNULL, returning only start_action_completed/returncode/target: pal_plugin/pal_shell_remote/slot.py:103-123 (https://github.com/OtakuNathan/pal-shell-native/blob/f307c9614634dd62a97bd1429d967a1c55489896/pal_plugin/pal_shell_remote/slot.py#L103-L123), pal_plugin/pal_shell_remote/slot.py:266-281 (https://github.com/OtakuNathan/pal-shell-native/blob/f307c9614634dd62a97bd1429d967a1c55489896/pal_plugin/pal_shell_remote/slot.py#L266-L281)

What the model actually sees: a broad SSH failure class, or the start action's exit code. It cannot distinguish specific host-key/identity/forwarding/network errors, nor see why the start script failed.

Minimal fix: keep a capped, sanitized stderr tail/diagnostic file and reference it on failure; do not capture unbounded stdout of the long-lived tunnel. Here the capture layer actively discards it; it is not a secondary omission by the llm_text renderer.

A11 · Conditional gap: the handler affordance is chosen first and filtered afterward, which may drop the fallback as well · P2, not proven to necessarily trigger in ordinary deployments

resolve_failure_guidance does not choose the descriptor fallback whenever any resolvable handler action exists; only afterwards does the finalizer filter that action by captured generation/schema/target/role. If all are filtered out and there is no handler hint, the result is empty, with no second fallback selection: src/pal/execution/result_guidance.py:124-130 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/result_guidance.py#L124-L130), src/pal/execution/runtime.py:1250-1289 (https://github.com/OtakuNathan/Pal/blob/b76358fb1a8488abae4745d0826564d75e2415a1/src/pal/execution/runtime.py#L1250-L1289)

This demonstrates a hole in one combinatorial branch, not that every built-in success/failure will encounter it. The minimal fix is to filter first and then pick the best, or, after filtering, provide a textual recovery hint applicable to the current role. Recovery hints must not expand role permissions. Do not re-present filtered, unavailable tools as executable actions.

Appendix C: Parameter combinations and state constraints

Scope and conclusions

Below, P denotes the Pal fixed source (https://github.com/OtakuNathan/Pal/tree/b76358fb1a8488abae4745d0826564d75e2415a1), and N denotes the native fixed source (https://github.com/OtakuNathan/pal-shell-native/tree/f307c9614634dd62a97bd1429d967a1c55489896). Line numbers after paths correspond to these two revisions. N's capabilities.py, tools.py, guidance.py, adapter.py, and router.py are all under pal_plugin/pal_shell_native/. In P, generated_tool_models.py always refers to src/pal/execution/generated_tool_models.py; within the same section, omitted browser file paths are based on src/pal/web_fetch/, proactive on src/pal/proactive/, v2 on src/pal/bunshin/v2/, and lsp on src/pal/lsp/; other omitted files follow the nearest preceding full directory.

The inventory covers model declarations, public alias registration, and relevant handler/service branches, including in-scope Bunshin tools. The following three categories must not be conflated:
- Hard constraint: the combination is invalid and the call is rejected
- Selection/override: the combination is accepted, but one field overrides another or has no effect at all
- State precondition: validity depends on the current state of a selected session, task, file, or target

Conclusion: there is indeed a gap where "the schema shows individual fields but not combination rules." The clearest cases are shell_session, bunshin_start_workflow, proactive schedule, mcp_image_prepare, and several browser/memory tools reused across operations. Meanwhile, browser_find's XOR, read_file's ranges precedence, case memory's STAR requirement, etc. are already documented and must not be double-counted as defects.

Scope boundary: excludes arbitrary third-party dynamic MCP/provider custom schemas; does not exhaustively cover the recursive semantics of architecture artifact documents or arbitrary policy/config dictionaries; the native C++ reactor and the full platform state machines of independent remote Bunshin/workers are not within this appendix's exhaustive claims. The following are confirmed items for the checked tool surface only and do not represent the full set of constraints of all installable plugins.

A. Native shell and target

A1. shell_session: exact parameter matrix per action

Type: hard constraint. Status: partially documented; key allowlist missing.

Aside from action, session_id/output_ref, the allowed non-null control fields are as follows:

- action:read
  Required: none
  Optional: wait_ms

- action:write
  Required: text, empty string allowed
  Optional: none

- action:resize
  Required: rows and columns filled together
  Optional: none

- action:terminate
  Required: none
  Optional: none

- action:release
  Required: none
  Optional: none

- action:watch
  Required: wait_ms > 0
  Optional: extend_by_ms, may be 0

- action:extend
  Required: extend_by_ms > 0
  Optional: none

- action:unwatch
  Required: none
  Optional: none


All other non-null fields are rejected. Therefore write+wait_ms, resize+wait_ms, and read+extend_by_ms are not free combinations. Explicit null on nullable control fields counts as not provided. watch's wait_ms=0 and extend's extend_by_ms=0 pass the field ge=0 check but are still rejected by the model_validator.

The current guidance explains action meanings but lacks a complete allowed/forbidden matrix; field descriptions are not filled in either. The validator has not become a conditional JSON Schema.

Suggested desc:
“read: optional wait_ms; write: text; resize: rows+columns; watch: positive wait_ms, optional extend_by_ms; extend: positive extend_by_ms; terminate/release/unwatch: no controls. Omit controls not listed for the action.”

Combination necessity: multiple distinct actions share one field table; it suits splitting into per-action tools or a discriminated union; arbitrary combinations are not valuable.

Evidence: N pal_plugin/pal_shell_native/tools.py:22-43; guidance.py:36-61.

A2. shell_session: session_id/output_ref and the recovery branch

Type: hard constraint. Status: output_ref purpose documented; XOR and wait prohibition not fully documented.

Exactly one of session_id and output_ref must be non-null. output_ref only supports read/release, forbids wait_ms, rejecting even wait_ms=0; combined with A1, this branch accepts no other control fields. output_ref must also point to an available, delivered retained result whose export failed; otherwise invalid_output_ref.

Suggested desc:
“Supply exactly one of session_id or output_ref. With output_ref, use read or release and omit all controls, including wait_ms.”

Combination necessity: retained_output_read/release could be separated from live session control.

Evidence: N capabilities.py:62-73,139-151.

A3. run_shell / run_shell_<shortcut>:sudo, target, tty

Type: hard constraint. Status: partially documented.

- target=0 is local; sudo=true+target=0 is rejected with sudo_unsupported
- Remote sudo=true+tty=true is rejected with privilege_pty_unsupported
- guidance documents the apt/apt-get update/install PACKAGE... syntax for Linux remote sudo, forbids extra flags/operators, and per-instance authorization, but does not explicitly state tty=false
- The configured generation fixes the target of run_shell_<shortcut>; the input model has no target; passing target is an unknown-field error and cannot override the target

Suggested sudo desc:
“Remote targets only; requires tty=false and an approved supported management command.”

Necessity of the combination: ordinary cmd/cwd/tty/wait/timeout combine naturally; sudo differs in command syntax, authorization, and PTY capabilities, so a separate privileged tool could be considered.

Evidence: N capabilities.py:18-35,284-325; router.py:127-136; guidance.py:64-87.

A4. run_shell: wait and timeout are independent; do not invent an inequality

Type: normal combination. Status: already sufficiently documented.

wait_ms controls how long this call waits before returning, not the process lifetime; timeout_ms is an optional hard deadline. When wait is omitted, PTY defaults to 1000 and others default to 300000. The Python boundary has no wait_ms <= timeout_ms requirement. cwd belongs to the execution target; the exported output snapshot path is on Pal's local host.

Suggestion: keep the existing guidance; do not add pseudo-constraints.

Evidence: N tools.py:14-19; adapter.py:129-147; router.py:147-157; guidance.py:8-17.

A5. shell_session: state preconditions, not a field-level XOR in this change

write/resize require a live PTY; release is used for output after completion; extend and watch positive-increment extensions require an existing extendable, unexpired finite deadline and never create a deadline out of thin air. Without a deadline it returns no_deadline; expired/terminating cannot be extended; signature-managed operations may return deadline_not_extendable.

The existing guidance already covers most of this. Suggested addition:
“Deadline extension requires an unexpired, extendable finite deadline.”

Evidence: N guidance.py:39-55; README "Session observation and deadlines (0.4.0)". This is the public state contract and does not claim to exhaustively describe the C++ state machine.

A6. list_remote, remote_start, remote_power

list_remote's target/refresh/view combine normally; omitting target lists all, selecting target limits the refresh scope, 0 is local; unknown target is rejected. remote_start's action must come from that target's configuration. remote_power only accepts shutdown and a positive target, and is limited by management capability/authorization; local 0 does not pass the schema.

Suggested remote_start.action desc:
“Exact start action advertised for this target by list_remote.”

Evidence: N capabilities.py:23-40,217-276. The specific per-target configuration validation of actions for remote background is outside the scope of this item-by-item verification.

B. Files, artifacts, discovery, and image input

B1. read_file: ranges takes precedence, not an XOR

Type: selection/ignoring. Status: already documented.

Non-empty ranges uses multi-chunk reading and ignores top-level offset/limit; each item in ranges has its own defaults, and each item is not required to explicitly provide both keys. Top-level fields still pass schema validation first, even if ultimately ignored.

Suggestion: no need to patch again; if writing it centrally, you could use "When supplied, ranges replaces top-level offset and limit."

Evidence: P src/pal/execution/generated_tool_models.py FileReadRangeItem/ReadInput; src/pal/execution/file_read.py:515-529,546-570.

B2. edit_file: correlation rules within a batch

Type: per-item/batch rejection. Status: mostly already documented.

old_string==new_string is rejected with NO_CHANGE; multiple matches require replace_all=true; all affected matches must lie within already-delivered and currently valid read ranges. All edits are applied against the same original snapshot, not executed sequentially. Overlapping items fail and are excluded, while other valid items may still succeed; a net overall change of zero is also rejected.

The existing edits desc/guidance already covers the original snapshot, overlap, partial success, unique matching, and read-before-edit; the fields do not explicitly state that the old and new text must not be identical.

Suggested addition:
“old_string must differ from new_string. Batch items match the same original snapshot; overlapping items fail.”

Necessity of the combination: batched editing has real value and should not be dismantled because of this.

Evidence: P src/pal/execution/file_capabilities.py:83-99; file_edit.py:120-148,280-307.

B3. delete_path: the file type determines the valid options

Directories require recursive=true and also reject a non-empty expected_sha256. Ordinary files may carry a digest; a mismatch rejects deletion. An ordinary file with recursive=true is not forbidden, so this is not a recursive/expected_sha256 XOR.

The existing description covers recursive's directory purpose and that the digest is for files, but does not explicitly state that directories cannot carry a digest.

Suggested expected_sha256 desc:
“Regular files only; omit for directories. Rejects deletion if bytes differ.”

Evidence: P src/pal/execution/path_delete.py:46-90; generated_tool_models.py DeleteInput.

B4. read_artifact: page/chunk and representation

page and chunk are mutually exclusive and the handler returns INVALID. page forces page_text and chunk forces chunk_text, overriding an explicit representation; it does not require the caller to also fill in a matching representation. Returns representation_unavailable when the selected representation does not exist.

The current fields already state the XOR and the corresponding representation; overriding an explicit representation could be stated more directly.

Suggestion:
“Use at most one of page or chunk; either overrides representation.”

Evidence: P src/pal/artifact/service.py:507-525,957-984; tools.py:145-164; generated_tool_models.py ArtifactReadInput.

B5. search_tools: precedence already documented; filters combine normally

When top_k and limit appear together, top_k takes precedence. namespace/family/module_name/tags jointly narrow the scope; tags requires all to match. Not an XOR; the existing field descriptions already document this.

Suggestion: no change; do not split orthogonal filter options into actions.

Evidence: P generated_tool_models.py SearchInput; src/pal/execution/tool_search.py search registration and handler.

B6. call_tool: args depends on the contract pointed to by name

name must be a callable indirect alias, and args must conform to the selected tool's schema; the dict is not free-form content. This dependency is inherent to indirect calls; read_tool/search_tools can discover the target input contract, and building one giant union covering all tools is not appropriate.

Suggested args desc:
“Arguments matching the selected alias's input schema.”

Evidence: P src/pal/execution/tool_search.py:51-80 and registry dispatch.

B7. mcp_image_prepare: the hidden precedence of source/mode

Type: choice/ignore; only reject when a usable source is missing. Current state: clearly missing.

Actual order:
1. url non-empty and mode=auto/url: return the URL directly, ignore artifact_id/path
2. Otherwise artifact_id non-empty: use the local path from artifact metadata to override path
3. Otherwise use path; if no usable local path, report artifact_id, path, or url is required
4. mode=path returns the path; mode=data_url returns data_url kind; artifact_id+auto/url also returns data_url kind; other local branches return base64 kind with payload containing both base64/data_url

So url combined with path/base64/data_url will not download and convert first; it fails due to having no local source. Filling all three sources is not an XOR; the expected source may be silently chosen incorrectly.

Recommendation:
“Choose one source for clarity. url is used only with auto/url and takes precedence. Otherwise artifact_id overrides path; path/base64/data_url need a local file or artifact. auto uses URL as-is, artifact as data URL, or path as base64.”

Necessity of splitting: it would be better to split by source union and output format; adding a source XOR would be a behavior change and cannot masquerade as an existing rule.

Evidence: P src/pal/mcp/plugin.py:459-525; generated_tool_models.py ImagePrepareInput.

E. Proactive and package

E1. proactive_create / proactive_update_schedule

The schedule schema is a dict, yet the handler imposes hard branch constraints:
- only cadence/timezone/cron/run_at_utc are allowed, and provided values must be non-empty strings
- manual allows only cadence/timezone
- cron requires cron and forbids run_at_utc
- once requires run_at_utc and forbids cron
- when cron/run_at_utc is present, cadence must also be explicitly present
- create with schedule omitted defaults to manual/UTC; update requires schedule
- timezone must be a valid IANA zone; for once, a timezone-naive time is interpreted in that timezone, a time with an offset keeps its meaning and is then converted to UTC; the final time must be in the future

The current desc gives example shapes and the future-time requirement, but does not fully cover forbidden keys, explicit cadence, or naive datetimes.

Recommendation:
“manual: cadence plus optional timezone; cron: cadence=cron + cron; once: cadence=once + run_at_utc. Do not mix cron/run_at_utc or supply either without cadence. timezone defaults UTC and interprets naive once times.”

Composition necessity: a typed discriminated schedule union is better than continuing to pile up dict descriptions.

Evidence: P src/pal/proactive/capabilities.py:713-793; the corresponding CreateInput/UpdateScheduleInput in generated_tool_models.py.

E2. proactive_create:out_channel_name/out_reply_target

If both are omitted: an existing task with the same name keeps its destination; a new session task resolves to the current conversation; some non-conversation/internal scenarios may have no output. If a channel is specified without a target: resolve to that channel's default. An explicit target can be resolved in combination with the requested/existing/current channel. create has no general constraint of "once a target is given, the channel must be explicitly given". The existing description is largely sufficient.

Evidence: P proactive/capabilities.py:376-396.

E3. proactive_set_output_channel

Omitting or leaving out_channel_name empty clears the output, but a non-empty out_reply_target is rejected in that case; an empty target is allowed. When the channel changes, the target is resolved together with it and does not carry over from the old channel's target. Currently partially described; the explicit forbidden combination is missing.

Recommendation:
“To clear output, omit/empty the channel and omit/empty the target. A nonempty target requires out_channel_name.”

Evidence: P proactive/capabilities.py:527-543.

E4. package_status

A non-zero wait_ms requires a truthy job_id; wait_ms=0 with no ID is allowed to list recent jobs. The field is already documented; this is not a hidden defect.

Evidence: P src/pal/packages/tool_models.py:18-20; jobs.py:92-101.

F. Bunshin public tools

F1. bunshin_start_workflow: existing task vs. new/reused

A non-empty task selects an existing actor-owned active Task; simultaneously providing a truthy workspace or a non-empty profile is rejected, since both belong to the Task. When task is omitted, profile must be resolvable and workspace must be provided; title defaults to goal and then falls back further. profile already states it is required when task is omitted, but workspace has no equivalent note. Reuse matching is based on workspace/objective/profile/owner, not just title. The same Task may not have another active workflow; this is a state restriction.

Recommendation:
“Existing task: supply task and omit profile/workspace. Otherwise supply profile and workspace to create or reuse the task.”

Composition necessity: the existing/new two branches suit a union or separate entry points.

Evidence: P src/pal/bunshin/v2/capabilities.py:119-149,458-480; service.py:343-387,587-631.

F2. bunshin_start_workflow:operation payload

new_requirement requires a non-empty goal and a non-empty task_spec, or a task_spec generated from task_spec_file. The other four operations require an artifact and forbid task_spec/task_spec_file. execute_trusted requires an internal trusted artifact; review_then_execute requires an external architecture; software_engineering review_and_repair requires a bounded ContractArtifact from a single produce-module.

The current guidance explains purposes, but the hard composition rules are incomplete. Errors return INVALID; it cannot be promised that all such errors are globally side-effect-free, because the service may have already created/reused a Task before later task_spec checks.

Recommendation:
“new_requirement requires goal and task_spec or task_spec_file. All other operations require artifact and forbid task_spec/task_spec_file. execute_trusted requires trusted architecture; software review_and_repair requires one implementation module.”

Composition necessity: starting from a requirement and routing to an existing artifact are better kept separate; the artifact content constraints must still be described.

Evidence: P v2/service.py:321-450; capabilities.py:133-183,206-209.

F3. bunshin_start_workflow: task_spec_file is not an XOR with the entire task_spec

task_spec_file and additional structural fields of task_spec may be passed together, but task_spec must not contain authoritative_text or authoritative_source. The existing description is quite explicit and should not be abbreviated into the incorrect "only one of them".

Evidence: P v2/capabilities.py:150-183; task_ledger.py:28-48.

F4. bunshin_start_workflow: workspace alias precedence

A non-empty repo_path takes priority; repo_root is only filled in when repo_path is missing/blank. The field text says both must be the same exact repository, but the normalizer does not validate their equality, so it cannot be claimed that a conflict raises an error. existing_repo/new_project additionally have path-existence/creation intent.

Suggested repo_root desc:
“Legacy fallback when repo_path is omitted; prefer repo_path and do not supply both.”

If equality enforcement is desired, a new validation should be added; this is an implementation change.
