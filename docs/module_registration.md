# Module registration ownership

Plugin registration is driven by `pal.core.registration_state`, rather than a
mutable `published` flag. A registration belongs to an exact `ModuleHandle`;
sharing its `module_id` does not confer withdrawal authority.

| Phase | Meaning and production boundary |
| --- | --- |
| `preparing` | `start(scope)` owns private resources and stages its handle. |
| `registered` | `MainContext.register_module` has acquired the name; PluginHost records `claim`. |
| `publishing` | PluginHost records `publish` before publishing providers, sources, handlers and capabilities. |
| `active` | Replay, subscriptions and attached status succeeded; PluginHost records `commit`. |
| `withdrawing` | The exact handle still owns the name. Revoke entry points and withdraw its public contributions before private cleanup. A failed withdrawal stays here for retry. |
| `cleaning` | No module registration is owned. Run private cleanup in reverse acquisition order; retain failures for retry. |
| `closed` | Resource and import cleanup completed. |

`PluginScope.begin_retirement` reads actual registry identity. An attempt that
never acquired the name goes directly to `cleaning` through `abandon`. It cannot
withdraw another module's published surfaces. If root registration acquired the
name but failed before PluginHost recorded `claim`, `preparing` can still retire
through `withdrawing`. Root registration starts shared rollback only after its
atomic name claim succeeds.

Publication observers and subscription replay retain unfinished compensation
against the exact handles that acquired it. Successful compensation steps are
not repeated; failed withdrawals or restoration of the previous projection stay
owned for retry. Final withdrawal after a failed refresh discards restoration of
that same handle and clears any partially restored projection instead. Withdrawing
a rejected replacement still restores a different, retained previous owner.
Unsubscribing an observer also discards its pending restorations and drains only
its own withdrawals; another observer's failure cannot block its retirement. An
observer cannot retire its resources while its own withdrawals remain unfinished.

Direct `MainContext.register_module` follows the same rule. A failed registration
revokes callback and control admission before retrying cleanup. If cleanup fails,
its unmounted handle retains the module name; callers retry
`unregister_module(handle)` before registering a successor. PluginHost retains
the equivalent scope as `cleanup_pending`. Neither path reports released
ownership while a derived projection still needs compensation.

Successful withdrawal releases the module name before private cleanup. A newer
instance may then claim that name even if the old instance retains failed
private cleanup. Retrying the old scope stays in `cleaning`; it does not repeat
public withdrawal against the new instance. Global module publication remains
serialized by the existing lifecycle writer; the registry locks make individual
name claims and releases atomic, without replacing that lifecycle admission.

Event sources have the same ownership rule. `EventSourceRegistry.attach` rejects
an occupied `source_id`, including a second registration of the same object.
Different modules cannot replace each other's source by choosing the same name.
Withdrawal supplies the original source objects and compares them with `is`;
stale cleanup cannot remove a replacement with the same textual id. Source ids
must be nonempty and stable for the lifetime of the registration.

PluginHost rejects an occupied module id before importing or starting the
candidate. Execution references declare `<module_id>:<local_name>`; L3 providers
must belong to `l3.<provider_id>`. MainContext validates these namespaces before
claiming or publishing a module. Execution and Memory reject duplicate claims
and compare the original provider object on withdrawal too. L3 registration is
owned by Memory, without an additional Execution registry entry.

## Executable relation and TLA+

The checked model is
[`ModuleRegistrationOwnership.tla`](../spec/core/ModuleRegistrationOwnership.tla).
Its phase transitions and name-ownership guards import
[`ModuleRegistrationReducer.tla`](../spec/core/ModuleRegistrationReducer.tla).
That support module is generated by executing the **production**
`reduce_registration`, `reduce_ownership` and `owner_relation` functions over
their complete finite inputs. It contains no separately maintained copy of the
transition rules. Module, event-source, Execution and L3 registries call the
shared ownership reducer; PluginScope and PluginHost use the registration reducer.

There are two checks on correspondence:

1. `scripts/run_tlc.py` compares the generated relation with the current
   production renderer before inventory validation or a TLC run. Ordinary CI
   rejects drift. `test_generated_tla_relation_is_the_complete_production_reducer`
   also checks every accepted and rejected reducer input. For every ownership
   input, all four real registry APIs must produce the same owner or
   rejection as the generated relation, including unchanged foreign owners.
2. `tests/test_registration_ownership.py` exercises real PluginHost boundaries:
   a failed claim against resident Core preserves its tools and prompts; a
   duplicate source rejects the candidate; an old scope's cleanup retry preserves
   a newer module and source. The existing publication/entry-withdrawal tests
   inject failures during publication, withdrawal and private cleanup.

The model represents two instances competing for one module name and a third
instance with another module name, all competing for one source name. It checks
that active registrations retain their name, capability surface and source;
cleaning/closed scopes own no module name; and every public surface belongs to
its current module registration. Partial acquisition and partial publication can
retire before commit.

| Configuration | Required TLC result |
| --- | --- |
| `ModuleRegistrationOwnership.cfg` | Exhaustive completion with ownership invariants intact. |
| `ModuleRegistrationForeignRollback.cfg` | Reject the mutant that lets an unclaimed attempt withdraw by name. |
| `ModuleRegistrationDuplicateSource.cfg` | Reject the mutant that replaces an occupied source name. |
| `ModuleRegistrationRetryWitness.cfg` | Reach an old active owner's failed cleanup being retried after its replacement becomes active. |

Observational history records whether an instance reached `active` and whether
`a0` retried cleanup while `a1` was active. This prevents a trivial witness in
which an attempt never published or retried before its replacement existed.
These observations do not restrict the model's transitions.

This establishes an exact generated reducer relation plus executable checks of
the host's side-effect boundaries. The handwritten orchestration abstraction is
not a machine-checked refinement proof of every Python statement. TLC checks
the stated finite instance and safety properties; it does not prove arbitrary
plugin cleanup terminates, or that an external plugin obeys the public lifecycle
contract. Already running ordinary event/timer callbacks retain their agreed
entry-check-only behavior.

Run the registration cases through the canonical runner (use a fresh output
directory):

```sh
python scripts/run_tlc.py --jar tla2tools.jar \
  --case spec/core/ModuleRegistrationOwnership.cfg \
  --case spec/core/ModuleRegistrationForeignRollback.cfg \
  --case spec/core/ModuleRegistrationDuplicateSource.cfg \
  --case spec/core/ModuleRegistrationRetryWitness.cfg \
  --output /tmp/pal-registration-check
python -m pytest -q tests/test_registration_ownership.py \
  tests/test_plugin_publication_rollback.py tests/test_plugin_entry_withdrawal.py
```

To regenerate after changing the production reducer:

```sh
python - <<'PY'
from pathlib import Path
from pal.core.registration_formal import render_registration_relation
Path('spec/core/ModuleRegistrationReducer.tla').write_text(render_registration_relation())
PY
```
