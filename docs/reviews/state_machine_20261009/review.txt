Audit comparison
F1: Fixed the gate acquisition ownership leak during duplicate cancellation of an ordinary task.
    The drain loop releases once only after acquire genuinely completes; cancellation waiting still relies on the holder eventually releasing.
F2: Fixed queued old bindings starting calls after unmount.
    The mount admission token is shared with the frozen registry, does not revive after revocation, and remounts use a new token;
    already-admitted calls are protected by a lifecycle read lease until completion.
F3: Fixed residual state from late attach failure after a generation was published; a successful rollback allows re-attach.
    A genuinely late cleanup failure retains the generation. Earlier failure phases still have R1 below.
F4: Fixed prepare prematurely consuming the cache tail; the commit moved to actual transport admission,
    including duplicate-notification and old-incarnation callback protection.
G1: Via an explicit no-throw contract for the core ownership listener and hardening the actual
    ResultSnapshotStore listener handling. Ordinary failures keep the old ownership and disable reclamation for life;
    cleanup/logging failures do not interrupt root publication. This is not a general isolation for arbitrarily throwing listeners.
G2: This is a clarification of contract scope, not a new file system atomic transaction.
    The supported verifier foreground writes/commits already have shared invocation/fence locks; external and background writes
    are not covered by this guarantee, and final settlement still requires re-verification. Receipt atomicity under arbitrary writes cannot be claimed.
G3: The model where endpoints no longer automatically fall back has been synchronized; the precision difference between L1 draft and item commit
    has been explained; no combined refinement proof was established.
G4: workflow is sorted by state before applying LIMIT, avoiding history crowding out active and masking duplicate active entries.
G5: Not done. There is no cross-subsystem composition proof, and no separate CI job pinned to a fixed TLC version.

Remaining reproducible issues (their implementations not yet modified)

R1 [P2] Rollback failure before generation establishment still loses ownership of pending-cleanup resources
Location: src/pal/plugins/host.py:851 (see also the ordering where generation is established only after capability publication).
Trigger: _publish_module_capabilities or another early attach phase throws, and one of the
cleanup callbacks in scope.close also fails. The branch that keeps the owner requires generation to be non-empty, which is not yet established at this stage.
Result: scope still has callbacks pending retry, but host.generations is empty and the state is load_failed;
the subsequent detach returns OK but no longer invokes that cleanup. Allowing subsequent attach may stack uncleaned resources.
Reproduced with both built-in plugins and third-party plugins. This gap existed before the patch; the package only fixed late publication.
Recommendation: establish a separate pending cleanup owner as soon as the scope/handle is obtainable, releasing it only on successful cleanup;
block duplicate attach even before formal publication, and provide a detach retry path.

R2 [P2] Execution extension activation failure with close failure has no retry entry point that keeps the candidate
Location: src/pal/execution/extensions.py:73; the empty-state return of uninstall is at lines 85-87.
Trigger: extension.activate throws; after rollback restores previous, extension.close(candidate) throws again.
Result: only an add_note is attached to the original exception; _installed remains empty, so a subsequent uninstall no longer calls close.
Resources held by the candidate implementation may be left behind. This gap also existed before the patch; the uninstall-failure retry newly added by the package only covers
extensions that were successfully installed, not installation failures.
Recommendation: save a separate failed-candidate cleanup owner, keep a close entry point, and allow repeated cleanup;
do not re-publish the failed candidate, and do not lose the restored original implementation.
