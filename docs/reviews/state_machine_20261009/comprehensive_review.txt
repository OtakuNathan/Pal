Pal State Machine and Resource Ownership Re-review (2026-10-09, Round 3)

Scope
This round traces real resource owners through normal unloading, failure rollback, cancellation, timeout, retry, package file replacement, provider construction, and
endpoint replacement; it also re-reviews execution entry mutual exclusion, FD leases, and
worker process reclamation. The first two rounds' review.txt, nightly_review.txt, and deep_review.txt
are historical records. This file, together with the evidence under wide/, describes this round's results.

Confirmed and Fixed Paths

1. Normal plugin detach did not reuse the full withdrawal barrier used for a failed attach.
   After surface withdrawal failed, resources its callbacks depended on could still be released.
   Normal unloading now also withdraws all entries first and only closes the scope on success; on failure the generation is retained.
   The generation/handle is removed only after the state record is written successfully; if recording fails, retry is still possible.

2. Package management treated attached=False as meaning no resources.
   A pending rollback from a failed build/failed attach may still hold resources; the old logic would replace or
   delete files it was still using. RuntimeActivation.before now checks generation,
   pending rollback, and provider handle. If candidate version cleanup fails, the candidate files are retained,
   and the old code is not restored to a path still occupied by new instances. Provider installation no longer unconditionally calls plugin
   entry restoration; it restores only when entries were actually withdrawn, avoiding masking the original error. CancelledError also enters the file rollback and
   the failure paths of install/uninstall state recording.

3. Provider factory, detach, cleanup, and import cleanup failures could lose the owner.
   A temporary handle is registered before construction begins; both callback and handle are removed only after success.
   Attach failure, discovery metadata failure, normal unload, reload, and shutdown all use the same ownership rule.
   Failed builds without discovery metadata also appear in management state and block loading of instances with the same name.

4. After a cleanup timeout or waiter cancellation, the same not-yet-completed cleanup could not be restarted.
   OwnedLifecycleStep retains the original Future/Task, and retries wait on the original task; the completion result is also retained,
   preventing a successful cleanup from being replayed when completion races with waiter cancellation. An asynchronous attach timeout must first
   wait for it to finish and receive the cleanup it returns before running detach. Callbacks that explicitly failed can be retried.

5. Transport stop failure was previously treated as license to discard metadata directly.
   Now the runtime retains the exact endpoint and the removal task; provider unload stops when it finds
   an unreclaimed transport, does not close provider resources, and does not delete the physical hub.
   Multiple removes share the same in-progress stop; an instance whose stop has already succeeded is not closed again because of a subsequent metadata
   failure. Retries of a failed reload also retain the attach intent in the repository.

6. After a candidate startup failure when replacing an endpoint, a candidate cleanup failure could still restore the old endpoint.
   Now failures in the preparation phase, the old-endpoint stop phase, and the candidate startup phase all retain the candidate resources;
   if candidate cleanup does not complete, the old transport is not restarted and the next replacement is not allowed.
   Hub deletion likewise checks for unregistered but still-owned candidates. A synchronous preparation failure before startup also retains
   the candidate cleanup owner; an asynchronous replacement before startup must register both in the registry and the hub transport.
   The endpoint base now explicitly declares lifecycle hooks, removing the redundant dynamic probing left over from the migration.
   A caller that cancels a replacement
   waits for the protected replacement task to complete its handover before receiving the cancellation exception.

7. Channel management tools did not take the execution lifecycle write lock.
   The aliases and canonical paths for provider reload / rescan and endpoint attach / detach / enable / disable /
   restart now use the same write barrier as plugin/package activation,
   avoiding concurrency with already-admitted calls and other lifecycle modifications.
   Direct Python calls to the internal manager API still require the caller to honor the lifecycle serialization contract.

8. PluginScope continued closing subsequent dependent resources when task cancellation was incomplete.
   Cleanup is now strictly LIFO, stopping at the first failed/incomplete step and retaining that step and earlier-registered
   dependencies. Already-successful steps are not redone. Only after a background task truly exits does a retry close its resources.

9. Top-level shutdown ignored child failures and continued closing dependencies and the database.
   PluginHost stops at the first cleanup failure in the dependency topology, keeping the managing owner and remaining dependencies,
   and reports shutdown_errors. The runtime must confirm that plugins and providers have finished shutting down before closing
   the resident services and the database; failures propagate to the caller, and successful hooks are not re-executed on retry.
   ShutdownDependencies with a positive case and deliberately-ignored-failure negative configurations covers this dependency chain.

Correspondence between TLA and the implementation
The generated reducer for EndpointHubLifecycle only constrains the hub state and cannot prove the Python
resource ownership above. New ProviderCleanupOwnership: one positive configuration plus four independent negative configurations, checking
owner retention, a single pending invocation, transport-before-close, and no duplicate execution of successful results.
Concrete mappings and boundaries are in spec/channel/ProviderCleanupOwnership.txt; the top-level shutdown is in
spec/core/ShutdownDependencies.txt.
Each of the four mutants must violate exactly the specified invariant; parse errors, timeouts, and empty state spaces do not count as passing.
The nightly conformance run adds provider cleanup, replacement cleanup, and package owner
regressions. The existing nightly schedule at 02:00 UK time is retained; local changes have not yet been published to the default branch.

This is not a full formal proof of the implementation: the new models are hand-written, with at most two attempts per layer, and prove only limited safety properties.
A failing or permanently hung third-party hook can retain the owner indefinitely; unloading is not guaranteed to complete.
Raw FD close does not use the ordinary callback retry semantics: FdLease does not determine whether to enter quarantine after closing;
the worker process instead first confirms process-group and pipe reclamation, then releases registration and workspace. Neither of these two places has been confirmed
to have the new same-kind owner-loss problem.
