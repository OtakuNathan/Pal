R4: Extension activation failure plus recovery of the old implementation failing again loses the cleanup owner of the candidate implementation
Location: src/pal/execution/extensions.py:44, 129.
The old exception path restored first and registered _pending_cleanup afterwards; a restoration failure skipped registration, and the candidate entry point remained alive.
Now restoration/shutdown obligations are registered first, then the candidate entry point is withdrawn; uninstall retries restoration and shutdown in order.
When restoration succeeds but close fails, neither is restored or republished again; a new install remains blocked.
Formal regression coverage includes candidate entry point call rejection, repeated restoration failure, subsequent close failure, and host/scope integration.
New ExtensionRollback positive and negative cases; the old lost-owner path triggers CleanupOwned.

R5: Async start/late publish cancellation bypasses rollback, and cancelling enable also leaves enabled=True behind
Location: src/pal/plugins/host.py:385, 856; src/pal/plugins/lifecycle.py:397.
CancelledError is not an Exception. The old implementation neither rolled back a cancelled start nor recorded the cancelled
async cleanup as pending retry; the outer enable's setting restoration was likewise skipped by the exception.
Now start/publish cancellation rolls back first, then propagates the cancellation as-is; a cancelled cleanup is retained, while other successful
callbacks are not duplicated; enable restores prior settings via finally.
Regressions cover first-party and third-party plugins, early start and late replay, and cleanup success/cancellation.
The model's Fail is an abstract failure edge; it alone cannot prove that Python exception categories were mapped correctly.

R6: When registry withdrawal also fails after a publish failure, resources get closed while the old entry point remains callable
Location: src/pal/plugins/host.py:882, 981; src/pal/execution/runtime.py:566.
The old rollback caught withdrawal errors and continued to scope.close; in a real reproduction, after cleanup the old captured entry point
still executed its handler successfully. A late generation's failed detach retry could also mark it back as attached.
Now the admission of this mount incarnation is withdrawn independently, without relying on a registry recompile; the mounted
marker is kept for removing residual metadata. Before other publish callbacks are withdrawn successfully, resources are not closed, handles are not dropped,
and cleanup contexts are not imported. A committed rollback retry no longer takes the attached=True fallback branch.
During the error period, tool discovery may still contain metadata for rejected calls; we do not claim all metadata is immediately deleted.
Regression coverage spans before/after generation establishment, persistent withdrawal failure, old calls being rejected, resources being held, and a subsequent successful
cleanup without duplication. PluginPublicationLifecycle adds an independent withdrawal phase and CleanupAfterWithdrawal,
plus a new counterexample for early resource closure. The model's callable surface and the still-to-be-withdrawn callbacks are now separate.

R7: CI accepts a "successful" model check with an empty initial state
Location: scripts/run_tlc.py:115.
Running Init == x \in {} on real TLC yields exit 0, a success message, and 0 distinct states;
the old verdict would falsely report a pass. It now requires the positive case to complete, the final queue to be empty, and distinct states > 0.
The stricter criterion was re-checked against all 106 pass logs from previous rounds; no normal results were falsely rejected.
The input hash is now computed from the files actually copied to TLC, avoiding source/execution byte mismatches caused by local edits.

R8: After import cache cleanup fails in the final step of a normal detach, a retry falsely succeeds
Location: the end of _detach_generation in src/pal/plugins/host.py.
The old order deleted the generation/handle maps first, then cleaned the import cache; an error thrown by the latter lost the owner,
and the next detach saw no generation and returned success directly, without retrying the failed step.
Now the owner is released only after import cleanup and state writing complete; failures retry along the existing committed-cleanup branch.
Regressions for both first-party and third-party plugins fail before the fix and succeed after it, and already-completed resource callbacks are not duplicated.
