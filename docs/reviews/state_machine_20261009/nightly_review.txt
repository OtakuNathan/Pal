R3: multiple prepares sharing a commit sequence number can cause a subsequent real admission to be ignored (fixed)
When the same coordinator scope held two not-yet-committed plans, the original implementation used
submitted_sequence + 1 for both; after the first commit, the second was misjudged as a duplicate notification by sequence deduplication.
The old PromptCacheTail retained only one pending payload and could not cover this interleaving.
This is a reproduced defect at the coordinator boundary; it has not been proven that the main conversation path ever actually triggered it concurrently.

Now each plan holds an independent single-use admission token, and the prepare sequence number is decoupled from the actual commit count;
a short late-arriving tail no longer rolls back an already committed longer position. Protections against duplicate notifications, expired generations,
and scope rebuild after closure and eviction are retained. Production tests cover both admission orderings plus duplicate notifications; the old implementation had 2 failed,
and passed after the fix. Two new PromptCacheAdmission configurations were added: the positive cases pass, and the old shared-sequence mutant
triggers SubmittedCountExact. It remains an independent model from PromptCacheTail, not a compositional proof.

Still unproven
The handwritten TLA and all Python paths still lack a mechanical refinement proof; the independent model does not prove cross-subsystem composition.
The atomicity of external file writes relative to the verifier durable receipt, and the termination of arbitrary third-party callbacks,
are still outside the guarantees of the existing contracts. Nightly CI can catch modeled and tested regressions, but cannot eliminate these proof boundaries.
